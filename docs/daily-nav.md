# 일별 NAV·기준가 원장 기반

`phalanx nav`는 사용자가 정규화한 원장과 일별 평가자료로 NAV·기준가·수익률·MDD를 계산하고 SQLite에 저장하는 오프라인 기능입니다. 저장 원본과 개정 이력에서 공백을 순서대로 복원합니다. 기존 계좌 스냅샷, `account overview`, 두 스냅샷의 Modified Dietz `account performance`와는 독립된 입력·저장 구조입니다.

**공식 성과 설정일은 주요 기능 개발이 끝난 뒤 사용자가 직접 지정합니다.** 오늘, 프로그램 설치일, 최초 조회일을 자동으로 사용하지 않습니다. 이 문서의 날짜·종목·금액·벤치마크 수준은 모두 합성이며 공식 성과를 개시하지 않습니다. 실제 자격증명이나 KIS 계좌 접근 없이 실행할 수 있습니다.

## 실행 예시

저장소 루트에서 실행합니다. `--db`는 매번 명시해야 하며 기본 경로나 자동 공식 계열이 없습니다. 예시는 `runtime/` 아래 개발 전용 저장소를 사용합니다. 실제 자료는 저장소 밖의 private 디렉터리에 보관하세요.

```bash
uv run phalanx nav import \
  --db runtime/nav-demo/daily.sqlite3 \
  --input examples/daily-nav/01-seed.json

uv run phalanx nav restore \
  --db runtime/nav-demo/daily.sqlite3 \
  --series synthetic-demo --environment development --through 2026-01-09

uv run phalanx nav query \
  --db runtime/nav-demo/daily.sqlite3 \
  --series synthetic-demo --environment development
```

첫 파일에는 사용자가 명시한 2026-01-05 장 마감 후 시작 상태, 매매·결제·외부 입출금·배당·이자·수수료·세금과 평가자료가 있습니다. 1월 7일 평가자료만 의도적으로 빠져 있어 1월 5~6일은 확정되고 7~9일은 미확정입니다. 복원 요청은 데이터 부족도 결과에 남기므로 성공 코드 `0`이어도 각 행의 상태와 사유를 확인해야 합니다.

다음 자료를 보완하면 그 이후를 다시 계산할 수 있습니다.

```bash
uv run phalanx nav import \
  --db runtime/nav-demo/daily.sqlite3 \
  --input examples/daily-nav/02-complete.json

uv run phalanx nav restore \
  --db runtime/nav-demo/daily.sqlite3 \
  --series synthetic-demo --environment development --through 2026-01-09
```

이제 5일 모두 확정됩니다. 설정일 NAV는 `20050`, 기준가는 `1000`이고 설정일 좌수는 `20.05`입니다. 정정 전 1월 9일 NAV는 `21405`입니다. 기준가·수익률에는 외부 입출금으로 조정된 좌수를 사용하므로 NAV 증감률과 같지 않습니다.

과거 배당 금액과 가격을 정정하는 예시입니다.

```bash
uv run phalanx nav import \
  --db runtime/nav-demo/daily.sqlite3 \
  --input examples/daily-nav/03-correction.json

uv run phalanx nav restore \
  --db runtime/nav-demo/daily.sqlite3 \
  --series synthetic-demo --environment development --through 2026-01-09

uv run phalanx nav history \
  --db runtime/nav-demo/daily.sqlite3 \
  --series synthetic-demo --environment development
```

정정은 1월 6일 배당 발생액을 `100`에서 `110`으로, 종가를 `1100`에서 `1150`으로 바꿉니다. 이미 수령한 배당 결제액 `100`은 그대로이므로 미수금 `10`이 남고 최종 NAV는 `21415`가 됩니다. 가격 정정은 다음 날 출금 좌수에도 영향을 주므로 이후 기준가·수익률·MDD까지 재계산합니다. `history`는 원본 입력 내용도 출력하므로 실제 자료의 출력은 공개 로그에 남기지 마세요.

동일 파일을 반복 import하거나 같은 구간을 반복 restore해도 거래를 재차 적용하지 않습니다. 프로세스를 종료하고 다시 실행해도 같은 SQLite를 열면 이어서 조회·복원할 수 있습니다.

## 명시적 설정과 데이터 구분

모든 입력 묶음은 `schema_version: "1"`, `series_id`, `environment`를 가집니다. `environment`는 `development` 또는 `official`이며 모든 저장·조회는 `(environment, series_id)`로 구분합니다. 개발용과 공식용은 별도 DB 파일을 사용하면 운영상 분리도 명확해집니다. 공식 입력은 사용자가 명시한 `official`과 설정 상태를 가져야 합니다. 개발 데이터를 공식 데이터로 자동 승격하지 않습니다.

선택 필드 `inception`은 사용자가 지정할 때만 넣습니다. 그 안에는 동일한 `series_id`, `environment`, `inception_date`, `initial_state`, `cash_flow_policy`, `benchmark_id`, `source_ref`가 필요합니다. `initial_state`는 현금 `cash`, 종목별 보유수량 `positions`, ID별 미수금 `receivables`, ID별 미지급금 `payables`를 모두 명시합니다. 항목이 없으면 `{}`로 명시합니다. 시작 보유수량을 포함한 전체 상태는 영속 보존하며 최초 기준가는 `1000`으로 고정합니다.

설정 상태는 **설정일 장 마감 후 상태**입니다. 설정일까지의 거래는 이 상태에 이미 반영되어 있어야 하며 그 날짜 이전이나 당일 사건을 원장에 다시 넣을 수 없습니다. 설정일 가격·벤치마크와 완전성 선언도 있어야 첫 NAV와 좌수가 확정됩니다. 보유자산이 없는 날에도 `prices: {}`를 명시합니다. 설정일 NAV는 양수여야 합니다.

기존 설정을 다른 날짜나 상태로 다시 import해서 초기화할 수 없습니다. 다른 시작 기준이 필요하면 기존 자료를 보존한 채 새 계열 ID를 지정합니다. 현재 구현은 설정 자체의 개정 기능을 제공하지 않습니다.

## 정규화 입력

금액·수량·가격·지수 수준은 JSON의 십진 **문자열**로 기록합니다. 예: `"1000.25"`. 이진 부동소수점 숫자로 전달하지 않습니다. 중복 JSON 키, 알 수 없는 필드와 잘못된 날짜·종류·개정은 거부합니다. `source_ref`는 각 설정·사건·평가자료의 출처 참조 문자열입니다. 실제 계좌번호나 자격증명을 참조값에 넣지 마세요.

`events`와 `days`는 추가하거나 정정할 항목만 담는 목록입니다. 생략한 기존 항목을 삭제하거나 거래 없음으로 해석하지 않습니다. 사건에는 안정된 `event_id`, `date`, 같은 날의 실행 순서 `sequence`(0 이상 정수), `kind`, 양의 `amount`, `source_ref`가 필요합니다. 같은 계열에서 `event_id`는 거래의 동일성을 판정하므로 원본 자료가 같으면 재수집·정정 때도 유지합니다. 서로 다른 ID로 복사한 거래의 동일성까지 추론하지는 않습니다. 같은 날 활성 사건의 `sequence`는 겹칠 수 없습니다.

| `kind` | 필요한 추가 필드 | 반영 방식 |
| --- | --- | --- |
| `buy` | `instrument`, 양의 `quantity` | 보유수량 증가, 사건 ID의 미지급금 생성 |
| `sell` | `instrument`, 양의 `quantity` | 보유수량 감소, 사건 ID의 미수금 생성 |
| `dividend`, `interest` | 없음 | 해당 사건 ID의 미수금 생성, 운용손익 반영 |
| `fee`, `tax` | 없음 | 해당 사건 ID의 미지급금 생성, 운용손익 차감 |
| `settle_receivable` | `reference_id` | 해당 미수금 감소, 현금 증가 |
| `settle_payable` | `reference_id` | 해당 미지급금 감소, 현금 감소 |
| `deposit`, `withdrawal` | 없음 | 현금과 좌수 조정, 외부 입출금으로 구분 |

매매의 `amount`는 매매대금입니다. 별도로 사건을 기록하는 수수료·세금을 대금에 또 포함하지 않습니다. 결제는 기존 채권·채무의 잔액 범위 내에서 부분 결제가 가능하며 별도 운용손익을 만들지 않습니다. 같은 날 발생과 결제가 있으면 발생 사건의 `sequence`가 먼저여야 합니다. 이미 지급된 배당·이자도 발생과 결제 두 사건으로 표현합니다. 배당의 발생일은 검증된 권리·회계 자료로 지정해야 하며 이 엔진이 배당락일이나 지급일을 추정하지 않습니다. 시작 미수금·미지급금은 시작 상태의 ID로 결제합니다.

일별 `days` 항목은 `date`, `ledger_complete`, `prices`, `benchmark_close`, `source_ref`가 필요합니다. `ledger_complete: true`는 해당 날짜의 거래·결제·권리·입출금 전체를 확인했다는 사용자 선언입니다. 입력 사건이 없다는 사실만으로 이 선언을 대체할 수 없습니다. 불완전한 날은 `false`, 부족한 가격은 해당 종목을 생략, 부족한 벤치마크는 명시적인 `null`로 남길 수 있습니다.

근거가 있는 가치 `0` 평가는 가격 `"0"`으로 명시할 수 있지만 가격 누락을 `0`으로 치환하지 않습니다. 벤치마크 수준은 양수여야 합니다.

정규화 종가는 현금배당과 권리를 별도 원장으로 반영하는 정책에 맞는 실제 평가가격이어야 합니다. 기존 일별 수정주가를 자동 연결하거나 배당 반영 가격과 현금배당을 함께 넣으면 이중 반영될 수 있으므로 자료 형식 검증이 필요합니다. `benchmark_id: "KOSPI_TR"`은 KOSPI Total Return 수준을 의미합니다. 단순 KOSPI 가격지수를 대신 넣지 않습니다. 엔진은 공급자가 실제로 올바른 지수를 제공했는지 외부 검증하지 않습니다.

## 계산 정책

모든 금액·좌수·수익률은 기존 50자리 Decimal context와 `ROUND_HALF_EVEN`을 사용합니다. JSON 결과의 수치는 십진 문자열이고 미확정 계산값은 `null`입니다. 수익률과 MDD는 퍼센트 표시값이 아닌 비율입니다. 설정일 이후 모든 달력 날짜를 평가하며 거래소 달력, 주말·휴일 가격 전달을 자동 추정하지 않습니다. 휴일에도 사용자가 원장 완전성과 평가가격·지수 수준을 확인한 일별 자료를 넣어야 합니다.

```text
NAV_t = 현금_t + Σ(수량_t × 가격_t) + Σ미수금_t - Σ미지급금_t
좌수_0 = NAV_0 / 1000
외부 순입출금 F_t = 입금 합계 - 출금 합계
좌수_t = 좌수_(t-1) + Σ_i(개별 외부 입출금_i / 기준가_(t-1))
기준가_t = NAV_t / 좌수_t
일별 수익률_t = 기준가_t / 기준가_(t-1) - 1
누적 수익률_t = 기준가_t / 1000 - 1
운용손익_t = NAV_t - NAV_(t-1) - F_t
낙폭_t = 기준가_t / max(설정일~t 기준가) - 1
MDD_t = min(설정일~t 낙폭)
벤치마크 기준가_t = 1000 × KOSPI_TR_t / KOSPI_TR_0
```

`cash_flow_policy: "previous_close_unit_value"`를 설정에 반드시 명시합니다. 모든 외부 입출금을 직전 확정 종가 기준가로 좌수로 환산하는 **장중 입출금 근사**입니다. 실제 입출금 순간의 기준가를 재구성한 정확한 장중 TWR이 아니므로 같은 날 시장 변동과 입출금 시점에 따라 성과 배분에 차이가 납니다. 기준가·좌수가 유효하지 않거나 상태의 일관성이 깨지면 확정하지 않습니다. 현재 지원 정책은 이것 하나입니다.

같은 날 입출금도 `sequence` 순서대로 개별 환산하고 각 연산에 고정 Decimal context를 적용합니다. 중간에 좌수가 0 이하가 되면 이후 입금으로 상쇄하지 않고 미확정으로 남깁니다.

설정일 기준가와 벤치마크는 모두 `1000`으로 시작하며 누적 수익률·낙폭·MDD는 기준점 정의상 `0`입니다. 설정일의 일별 수익률·운용손익·외부 입출금은 이전 평가 구간이 없으므로 `null`입니다. 이후 자료가 부족한 날짜에 수익률 `0`을 대입하지 않습니다. 벤치마크도 일별·누적 수익률과 MDD를 계산하며 `excess_return`은 포트폴리오 누적 수익률에서 벤치마크 누적 수익률을 뺀 비율 차이입니다.

## 공백과 정정

`restore --through`는 저장된 설정일부터 지정일까지 날짜순으로 계산합니다. 이전에 더 먼 날짜까지 복원했다면 그 날짜까지 유지하며 더 이른 `--through` 요청으로 이력을 잘라내지 않습니다. 미확정 날이 발생하면 이후 날도 이전 상태를 확정할 수 없으므로 미확정으로 이어집니다. 빠진 날짜·원장 완전성·가격·벤치마크를 보완한 뒤 다시 restore하면 이어지는 상태를 재현합니다. `query`는 현재 저장 결과를 읽으며 자동 복원 명령이 아닙니다.

각 결과는 `date`, `status`(`confirmed` 또는 `pending`), `reasons`, 계산값과 상태 `state`를 가집니다. 주요 미확정 사유는 다음과 같습니다.

| `reasons` 값 | 필요한 확인 |
| --- | --- |
| `missing_daily_input` | 해당 날짜의 평가·원장 완전성 자료 |
| `ledger_incomplete` | 해당 날짜의 거래·결제·권리·입출금 전체 확인 |
| `missing_position_price` | 보유 중인 종목의 평가가격 |
| `missing_benchmark` | 해당 날짜의 KOSPI Total Return 수준 |
| `preceding_day_pending` | 먼저 미확정인 이전 날짜 보완 |
| `unmatched_or_excess_settlement` | 원채권·채무 ID, 순서와 잔액 |
| `nonpositive_nav`, `nonpositive_units` | 양의 NAV·좌수를 유지할 수 없는 상태 |

최초 사건·일별 자료의 `revision`은 `1`(기본값)입니다. 이미 등록한 내용을 바꾸려면 같은 사건 ID 또는 평가 날짜에 다음 개정 번호와 `correction_reason`을 제공합니다. 같은 개정의 동일 내용을 재입력하면 중복 처리하지 않으며 같은 개정 번호로 다른 내용을 보내면 거부합니다. 사건 취소는 상위 개정과 `void: true`로 기록하며 원본을 삭제하지 않습니다. 사건 날짜를 이동한 정정은 원래 날짜와 새 날짜 중 더 이른 날부터 영향을 줍니다. 정정에 연결된 결제·원장 완전성도 사용자가 함께 확인해야 합니다.

입력은 SQLite 트랜잭션으로 반영되며 원본 입력 바이트의 해시와 원본, 개정 이력, 계산 이력을 보존합니다. `history.source_imports[].raw_payload_base64`는 원본 바이트의 Base64 표현으로 원본 인코딩·공백까지 복구할 수 있습니다. 입력 변경 뒤 해당 계열의 현재 파생 결과 전체를 무효화하므로 restore 전 `query`는 빈 배열을 반환합니다. 이전 결과는 계산 이력에 보존되며 restore는 전체 설정일부터 재계산하여 과거 정정의 모든 후속 영향을 반영합니다. 새 프로세스나 저장소 재개방 후에도 입력과 계산 상태를 읽을 수 있습니다. 매일 하루씩 restore한 결과와 동일한 자료를 한꺼번에 restore한 결과는 일치합니다.

각 `history.calculations[]`에는 당시 선택한 설정·원장·평가 개정본 전체인 `input_manifest`, 그 내용의 `input_sha256`, 계산 엔진 버전과 종료일도 저장합니다. 이후 정정이 생겨도 해당 계산에 사용한 입력을 직접 재구성할 수 있습니다. 현재는 전체 재계산과 계산별 입력·결과 보존을 우선하며 증분 계산 및 저장 용량 최적화는 후속 범위입니다.

## 저장과 오류 처리

SQLite 파일의 신규 생성은 `import`에서만 허용합니다. `restore`, `query`, `history`는 기존 DB가 없으면 실패하며 빈 DB를 자동 생성하지 않습니다. 저장 디렉터리·파일은 기존 private 저장 정책에 따라 소유권·권한과 링크를 검사하며 생성 디렉터리는 `0700`, DB와 보조 파일은 `0600`입니다. 잘못된 기존 권한을 자동으로 변경하지 않습니다. 현재 저장 어댑터는 Linux/WSL 환경을 대상으로 합니다.

최초 스키마는 같은 디렉터리의 private 임시 파일에서 완성한 뒤 기존 파일을 덮어쓰지 않고 원자적으로 설치합니다. 이후 입력과 복원은 SQLite 트랜잭션과 `FULL` 동기화를 사용합니다. 경로 검사는 링크·권한 오류와 일반적인 파일 교체를 탐지하며 같은 파일 소유자 권한을 가진 프로세스의 임의 파일 조작까지 격리하는 기능은 아닙니다.

CLI의 정상 출력은 JSON이며 오류는 민감한 원본 값·예외 상세를 포함하지 않은 메시지로 stderr에 출력합니다. 종료 코드는 옵션 누락·잘못된 선택값 `2`, 정규화 입력·계산 오류 `65`, 저장 오류 `66`, 예기치 않은 오류 `70`, 사용자 중단 `130`입니다. `history`를 포함한 정상 출력에는 요청한 자료가 포함됩니다.

기존 설정을 바꾸려는 입력, 같은 개정 번호의 내용 충돌, 개정 번호 누락과 없는 계열 등 저장 원장과 충돌하는 요청도 `66`입니다. 이런 경우 파일 권한만이 아니라 명시한 계열·설정·개정 관계를 확인하세요.

## 현재 제약과 후속 연동

KIS 과거 체결·권리·입출금의 자동 수집, HTS 엑셀 변환, 원장 완전성의 외부 확인과 실제 KOSPI Total Return 데이터 수집은 미구현입니다. 실제 자료 형식을 검증한 뒤 정규화 입력 어댑터로 연결할 예정입니다. 현재 명령은 KIS 네트워크·자격증명·토큰 캐시를 사용하지 않습니다.

단일 통화 계좌의 현금·주식 수량·미수금·미지급금과 위 표의 사건 종류를 지원합니다. 현물 입출고, 분할·병합·유상증자 등 별도의 보유수량 권리 처리, 외화·환율, 파생상품, 공매도·차입 및 장중 정확 평가 기능은 없습니다. 지원하지 않는 사건을 임의 입출금이나 매매로 치환하지 말고 별도 정규화 규약 검증 후 확장해야 합니다. 기존 KIS 스냅샷이나 현재가만으로 누락된 과거 원장을 완성할 수 있다고 표시하지 않습니다.

통화는 `KRW`이며 보유수량은 음수가 될 수 없습니다. 음수 현금 상태는 표현할 수 있지만 차입 잔액·약정·이자를 추정하지 않습니다. 발생 이자는 원장에 직접 넣어야 합니다. NAV 또는 좌수가 0 이하가 되면 미확정으로 남으며 전액 환매 이후 같은 계열을 자동 재설정하거나 재개하지 않습니다.
