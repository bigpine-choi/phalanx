# Phalanx — 네 엔진 아키텍처 제안

작성: 2026-09-30 KST  
상태: 설계안. 운용·연구·검증·감시로 역할을 나누는 개발 방향을 기록한다. 아래의 상세 구조와 개발 순서는 제안이며, 구현 완료나 실거래 활성화를 의미하지 않는다.

## 목표와 설계 원칙

목표는 투자 판단을 반복 가능하게 만들고, 성과의 원인을 검증하면서 사람의 반복 작업을 줄이는 것이다. 자동 주문 실행은 기술적 개발 목표가 될 수 있지만, 지속적인 초과수익은 별도로 실증해야 한다.

네 엔진은 네 가지 책임이다. 초기에는 기존 Python 프로젝트 안에서 모듈로 구현하고, 공통 데이터와 기록 형식을 사용한다. 각 엔진에 별도의 LLM이나 서버를 둘 필요는 없다. Godot는 사용자가 제안, 검증 근거, 운용 상태와 경보를 보는 화면을 맡는다.

## 역할과 권한

| 엔진 | 핵심 질문 | 입력과 산출물 | 권한 경계 |
|---|---|---|---|
| 연구 | 어떤 가설이 수익의 원천이 될 수 있는가? | 시점별 데이터와 가설 → 버전이 고정된 전략 후보·실험 기록 | 실거래 자격증명에 접근하지 않으며 운용 전략·한도를 변경하지 않음 |
| 검증 | 비용과 위험을 반영해도 근거가 남는가? | 후보·기준 전략·분리된 평가 데이터 → 비교 보고서·통과/보류 사유 | 승격 근거를 생성. 초기에는 사람의 전략 버전·운용 한도 승인 필요 |
| 운용 | 승인된 전략을 현재 상태에서 어떻게 실행할 것인가? | 승인된 전략·투자 정책·확인된 계좌 상태 → 목표 비중·주문 의도·실행 기록 | 지정된 전략 버전과 한도 안에서만 작동. 초기에는 주문 없는 모의 운용 |
| 감시 | 지금 운용을 계속해도 되는가? | 데이터 상태·주문·체결·잔고·위험 지표 → 허용/차단·경보·복구 상태 | 주문 전 제한을 강제하고 이상 발생 시 신규 주문을 차단. 전략을 임의로 생성·교체하지 않음 |

운용 엔진이 만든 주문 의도는 반드시 규칙 기반 사전 주문 검사를 통과해야 한다. LLM 답변으로 이 검사를 우회할 수 없도록 한다. 검사 대상은 가격의 최신성, 주문 가능 금액, 종목·총 노출 한도, 중복 주문, 계좌 상태 불일치 등이다.

감시는 두 부분으로 나눈다. 주문 경로 안의 동기식 검사와, 별도로 상태를 확인하는 비동기 감시다. 초기에는 한 프로젝트에 두되, 실거래 단계에서는 운용 프로세스 자체가 멈춘 경우를 감지하는 외부 감시도 필요하다.

신규 주문 중지는 보유 자산 청산과 다르다. 미체결 주문의 취소·유지, 기존 포지션 유지·축소, 재개 조건은 사전에 정의된 정책을 따른다. 감시가 시장 손실을 없애는 기능은 아니다.

## 네 엔진이 공유할 기반

[Jev 활용 계획](jev-integration-plan.md)은 이 구조 안의 교체 가능한 판단 모듈이다. 첫 적용은 연구 엔진의 뉴스·공시 분류와 검증 엔진의 비교 실험이며, 감시는 호출 실패·지연·검토 비율과 정정률을 관찰한다. 숫자·날짜·한도 검사는 Python에 유지하고, Jev의 확신 수치가 운용 권한이나 성과 검증을 대신하지 않는다. API 호출과 제품 기능 활성화는 아직 수행하지 않았다.

- **시점별 데이터:** 관측 시점과 실제 이용 가능 시점, 데이터 원천·수정 이력·스냅샷 식별자를 기록한다.
- **전략과 정책 버전:** 모델, 피처, 학습 구간, 설정, 투자 제약, 승인된 전략 버전을 묶어 재현 가능하게 보관한다.
- **의사결정 원장:** 제안, 검증 결과, 승인, 목표 비중, 주문 의도, 실제 주문·체결·취소를 연결한다. 모의 기록과 실제 기록은 명시적으로 구분한다.
- **주문·계좌 상태:** 주문 식별자를 고정해 중복 요청을 막고, 응답이 불확실하면 증권사 상태를 조회해 확인한 뒤 후속 조치를 결정한다.
- **실험 기록:** 성공한 실험뿐 아니라 탈락한 후보와 시도 횟수도 남긴다. 비교 결과를 본 뒤 같은 평가 구간에 반복적으로 맞추는 행위를 추적한다.

공통 식별자는 `decision_id`, `strategy_version`, `policy_version`, `data_snapshot_id`를 중심으로 잡는다. 구체적인 저장소와 스키마는 기존 코드 구조를 확인하면서 결정한다.

운용 엔진은 주문 접수 여부 불명, 부분 체결, 취소, 만료를 포함한 주문 수명주기를 책임진다. 재시작 시에는 증권사의 미체결·체결·잔고 상태와 대사한 뒤 운용을 재개한다. 자동 재시도만으로 주문 성공 여부를 추정하지 않는다.

## 검증 엔진의 기준

1. 단순한 기준 전략과 비교한다. AI가 추가한 효과와 시장·스타일·레버리지 노출을 구분한다.
2. 당시 이용할 수 있었던 정보만 사용한다. 미래 수익률을 학습 표적으로 쓸 때는 평가 시점 전에 표적 기간이 종료된 데이터만 학습에 포함한다.
3. 시간 순서대로 학습·검증·평가 구간을 나누고, 겹치는 표적 기간과 전처리에서 생기는 정보 누출을 차단한다.
4. 수수료, 세금, 슬리피지, 체결 가능성, 거래량 제약을 반영한다. 반영하지 못한 비용은 결과에 명시한다.
5. 종목 선택과 비중 배분을 각각 고정해 비교하여 성과 변화의 원인을 분리한다.
6. 비용 차감 수익률뿐 아니라 낙폭, 회전율, 노출, 국면별 성과와 불확실성을 함께 본다.
7. 과거 백테스트를 통과한 후보는 이후 시점의 주문 없는 모의 운용으로 추가 확인한다. LLM의 과거 지식 혼입 가능성 때문에 과거 뉴스 재해석만으로 실전 성과를 주장하지 않는다.

통과 기준과 평가 기간은 실험 전에 정한다. 반복 검증으로 평가 구간이 사실상 학습에 쓰였다면 새로운 평가 기간이나 이후 관측이 필요하다.

## 기존 Phalanx와의 연결

2026-09-29 GitHub 확인 기준으로 재사용할 기반이 있다.

- Python의 종목 탐색, 가격 이력·피처, 후보 선정, 자산 배분, NAV·성과 계산.
- Godot의 실제 보유 종목 조회, 시장·리서치 화면, AI 자문, 비중 시뮬레이터, 의사결정 기록.
- 숫자 계산과 계좌 상태 처리는 Python에 두고, LLM은 문서 해석·가설 제안·설명·반론 생성에 사용한다.

현재 시뮬레이터는 기존 보유 종목에 대한 비중 변경을 다루며, 실제 주문이나 완전한 거래비용·결제 모델을 제공하는 상태가 아니다. 실제 계좌 조회와 자동 주문 구현을 혼동하지 않는다. 운용 경로에 샘플 계좌나 가짜 가격을 다시 넣지 않는다.

Godot 화면과 장시간 실행되는 운용 작업은 인터페이스로 분리한다. 향후 자동 운용을 켠 경우에는 창을 닫아도 운용이 계속되는지 명확히 표시하고, 시작·일시정지·중단 상태를 확인할 수 있어야 한다. 화면 종료를 주문 상태 소실이나 무조건적인 주문 취소로 처리하지 않는다.

GitHub의 Godot 작업 브랜치와 Python main은 확인 당시 공통 Git 조상이 없었다. 네 엔진 설계를 일반적인 브랜치 병합으로 바로 적용할 수 있다고 가정하지 말고, 기존 실행 경로와 인터페이스부터 확인한다.

## 첫 구현 범위

기존 연구 자산의 적용 순서는 [기존 연구 코드 활용 로드맵](legacy-reuse-roadmap.md)을 따른다. 라니아케아의 데이터·모델 명세와 비교 검증(R1·R2)을 공통 기반에 우선 연결하고, 다기간 예측·혼합(R3·R4)은 연구 후보로, 배분 비교(R5)는 기존 계산의 확장으로, 뉴스 정찰(R6)은 후속 리서치 입력으로 편입한다. 모델 성과와 실거래 구현이 검증됐다는 의미는 아니다.

첫 목표는 **하나의 전략이 연구 → 검증 → 주문 없는 운용 → 감시 → 성과 재평가를 한 바퀴 도는 것**이다.

1. 공통 데이터 시점·전략 버전·의사결정 기록을 정한다.
2. 기존 후보 선정 로직에서 기준 전략 하나와 비교 후보 하나를 골라 동일 조건으로 평가한다.
3. 같은 의사결정 경로로 일별 목표 비중과 모의 주문을 생성한다.
4. 데이터 지연, 잔고 불일치, 중복 실행, 재시작 상황에서 차단·기록·복구 동작을 확인한다.
5. Godot에서 후보 근거, 검증 결과, 운용 제안, 감시 상태를 확인한다.

완료 기준은 같은 입력·버전의 결과를 재현할 수 있고, 모든 의사결정의 근거를 추적할 수 있으며, 이상 상태에서 다음 주문 의도가 차단되고 재시작 후 상태를 복원할 수 있는 것이다. 정해진 기간의 수익만으로 완료를 판단하지 않는다.

후속 단계는 승인된 제한 안의 소액 실거래, 관측 결과에 따른 운용 범위 확대, 투자자문·투자일임 서비스 요건 연구다. 실제 주문 연결과 활성화는 별도의 명시적 승인 뒤에 진행한다. 초기에는 새 모델·전략 버전으로의 교체와 위험 한도 변경에 사람의 승인을 유지한다.
